## 지금 어디까지 왔나

교실 크롬북(ARM Mali-G72 MP3, 1280×632)에서 **30fps → 33~35fps**.
큰 도약은 아직. 다만 **범인이 어디 없는지는 확실히 좁혔다.**

## 실측으로 배제된 것 (다시 파지 말 것)

크롬북에서 `?diag=1` + Shift+9 짝비교로 잰 값:

| 껐을 때 | 차이 |
|---|---|
| 해상도 0.85 / 0.70 / 0.55 | +2 / +3 / **+3** |
| 점광원 2개 | +1 |
| 바닥 조명 | −2 |
| 지형 전체 숨김 | 0 |
| **화면 그리기 전체** | **+3** |
| **게임 로직 전체** | **+21** |

- 해상도를 0.55까지 내려도 0.85와 같다 → **픽셀 문제 아님**
- 화면 그리기를 아예 꺼도 +3 → **GPU 아님**
- 지형을 통째로 숨겨도 0 → **삼각형 아님**
- 삼각형을 245K→103K로 줄였을 때도 +3뿐이었다

## 남은 문제

**게임 로직이 +21fps (약 11.8ms).**
그런데 구간별 측정기가 잰 로직 합은 **1.4ms**뿐이다.
→ **10.4ms가 rAF 콜백 바깥에서** 벌어진다. 측정기는 콜백 안만 잰다.

후보: HUD의 DOM 배치·그리기, GPU 프로세스로 가는 업로드, 쓰레기 수거.

## 2026-08-28 집에서 잰 것 — 결론 못 냄, 그러나 소득 있음

크롬북을 집으로 가져와 **혼자** 방을 만들어 두 번 쟀다. 둘 다 **못 쓰는 표**였다.

| | 1회차 | 2회차 |
|---|---|---|
| 기준 fps | 48~53 | **35~53 (9.7ms 흔들림)** |
| 게임로직 통째로 | +6 (2.31ms) | +1 (0.35ms) |
| 불가능한 음수 | 화면그리기 −2 | 캐릭터갱신 −4, 화면그리기 −3 |

2회차는 **이름표 단독 3.57ms 가 이름표를 포함한 넷다 끔 0.35ms 보다 10배** 컸다.
부분이 전체보다 클 수는 없다. → **밤 130초인데 스윕이 39초라, 재는 도중 낮이 됐다.**
늑대가 사라지고 뒤쪽 항목들이 전부 "한가한 낮"을 잰 것이다.

**소득 두 가지:**

1. 항목별 효과는 0.3~1ms 인데 **노이즈가 ±0.8ms 이상**이다.
   지금 방식으로는 네 조각의 순위를 못 매긴다. 더 크게 흔들리면 아예 못 쓴다.
2. **학교 33~35fps 도 혼자 잰 값이었다.** 사람 수는 원인이 아니다.
   그렇다면 집 50fps 와의 차이를 설명할 후보는
   **(a) `2e7ece0` 하단 바 수정이 실제로 들었다  (b) 발열·전원  (c) 와이파이** 셋이다.
   (a)가 유력하다 — `HUD 끔`이 이제 +1 뿐인 것은 **이미 싸진 걸 꺼서** 라고 보면 앞뒤가 맞는다.

## 2026-08-28 저녁 — 처음으로 노이즈를 뚫은 신호

새 계기(늑대 수 기록)를 넣고 집에서 혼자 다시 쟀다. **늑대24 로 완전히 고정된 구간**이
세 줄 있었고, 그게 유일하게 조건이 같았던 구간이다.

| 항목 | 비용 | 늑대 | 신뢰 |
|---|---|---|---|
| HUD 끔 | 0.71ms | 10~19 | ❌ |
| 캐릭터갱신 끔 | 0.00ms | 19~24 | △ |
| 이름표 끔 | −2.53ms | 24 | ✅ (음수 = 편향) |
| **시뮬·통신 끔** | **5.29ms** | 24 | ✅ |
| **넷다 끔** | **5.87ms** | 24 | ✅ |
| 게임로직 통째로 | 4.74ms | 3~24 | ❌ |
| 화면그리기 끔 | 0.79ms | 6~26 | ❌ |

**시뮬·통신 하나가 넷 전체의 90%.** 이전 측정은 죄다 0.3~1ms 라 순위를 못 매겼는데
이번엔 5ms 를 넘는다.

**그런데 `시뮬·통신` 은 통신이 주가 아니다.** 실제로 끄는 것은
`hostPhase / hostSim(늑대 시뮬레이션) / buildFlow(길찾기) / netTick / metaTick` 이다.
선생님이 host 라 **늑대 시뮬레이션 전체가 이 기기에서 돈다.**

기각된 가설: "학교가 느린 건 잴 때 늑대가 많아서"
→ 학교에서도 6~7일차 밤, 비슷한 늑대 수로 쟀다. 조건이 같은데 학교 30fps / 집 35~54fps.
   이 차이는 아직 설명 안 됐다. (남은 후보: 코드 변경, 발열·전원, 와이파이)

**다음에 할 일 — 늑대 시뮬 안쪽을 재라.**
`hostSim` 을 길찾기 / 늑대이동 / 밀어내기 / 타워 / 병정 으로 쪼개 뒀다.
`?diag=1` 화면의 `└시뮬 안쪽` 칸에 바로 뜬다. **Shift+9 안 눌러도 된다.**

의심 하나: 늑대끼리 밀어내는 코드가 모든 늑대쌍을 돈다(O(n²), `Math.hypot`).
24마리면 프레임당 552번, 54마리면 2862번.
다만 **개발 PC 에서 0.02ms 밖에 안 나온다.** 55배 차이를 감안해도 1ms 정도라
5.3ms 를 다 설명 못 한다. 그러니 **`·밀어내기` 값을 크롬북에서 직접 보고 판단할 것.**
(제곱거리로 바꾸면 PC 기준 16배 빨라지는 건 확인해 뒀다. 필요하다고 재진 다음에 고친다)

## 2026-08-28 밤 — 진단 화면 전체를 읽음. 네 개가 배제됐다

집 · 혼자 · 5일차 밤 · **늑대 24** · 건물 0 · Mali-G72 · 1423×702 · **49fps**

```
프레임 전체        20.00ms
├ 브라우저작업      9.19ms   <- 콜백 밖. 가장 큼
└ 콜백 안          10.81ms
   ├ ★그리기       7.16ms   <- 콜백 안 최대. 드로우콜 159개 = 콜당 45µs
   ├ 시뮬          1.18ms
   ├ 늑대          0.87ms
   └ 통신          0.43ms
   (+ DOM배치 2.79ms · HUD글자 0.55 · 미니맵 0.26 — 초당 8번만. 매 프레임 아님)
  └시뮬 안쪽: 늑대이동 1.11 / 밀어내기 0.20 / 길찾기 0.01 / 타워 0.01 / 병정 0.00
```

**배제된 것 (다시 파지 말 것):**

| | 값 | |
|---|---|---|
| 밀어내기 O(n²) 루프 | 0.20ms | 의심했으나 아님 |
| 시뮬 안쪽 전부 | 1.33ms | 늑대 시뮬레이션 아님 |
| 이름표재생성 | 0회/초 | 이름표 수정이 제대로 듣고 있다 (예전 75.7회) |
| 메모리 늘어남 | 0.0MB/초 | 쓰레기 수거 아님 |

**남은 모순 — 3.68ms 가 콜백 밖에 숨어 있다.**
같은 늑대24 조건인데 구간별은 `시뮬 1.18 + 통신 0.43 = 1.61ms`,
스윕은 `시뮬·통신 끔 5.29ms`. 차이 3.68ms.
가설: Firebase `.set()` 은 부르는 순간만 콜백 안이고, 진짜 직렬화·전송은
콜백이 끝난 뒤에 벌어져 `브라우저작업` 으로 들어간다. host 는 초당 7번 보낸다.
→ **Shift+7 로 시뮬·통신을 끄고 브라우저작업이 줄어드는지 보면 갈린다.**

**더 중요한 의심 — 평균이 아니라 튀는 문제일 수 있다.**
60Hz 화면에서 프레임은 16.7ms 아니면 33.3ms 로 떨어진다.
그 둘이 8:2 로 섞이면 평균이 정확히 20.0ms(=50fps) 가 된다. 실측이 그 값이다.
"고르게 느린 것"과 "대부분 빠른데 5프레임에 1번 놓치는 것"은
평균이 같아도 고쳐야 할 곳이 전혀 다르다.
→ **`★프레임분포` 줄을 보면 갈린다.**
   `빠름80% 한박자놓침20%` 이면 튀는 놈(초당 8번 DOM배치 2.79ms,
   초당 7번 Firebase 전송)을 잡아야 하고,
   `빠름100% 최악20ms` 면 매 프레임 비용(★그리기 7.16ms)을 깎아야 한다.

## 2026-08-28 밤 — 범인을 잡았다: Firebase 전송

새 계기 두 개로 두 가설이 동시에 확정됐다.

**① 고르게 느린 게 아니라 튄다**
```
★프레임분포  빠름70%  한박자놓침26%  더놓침4%   최악 50ms
```
10프레임에 3번 박자를 놓친다. 평균(20ms)만 봐서는 절대 못 봤을 모양이다.

**② 튀게 만드는 건 Firebase 전송**
`Shift+7` 로 시뮬·통신을 끄면 **브라우저작업이 확 준다.**
`.set()` 은 부르는 순간(통신 0.43ms)만 콜백 안이고, 직렬화·전송은 콜백이 끝난 뒤에
벌어져 콜백 밖 시간으로 간다. 구간별 합 1.61ms 인데 스윕이 5.29ms 였던
**3.68ms 차이가 이것이다.**

**고친 것 — 숫자 배열 대신 문자열 하나로 보낸다**
Firebase 는 배열을 숫자키 객체로 펼쳐서 칸마다 검사·해시를 한다.
늑대 25마리 + 병사 6명이면 **206칸**, 그걸 초당 7번 보내고 있었다.
문자열 하나면 **3칸**이다. 68배.

왕복 검사: 늑대 25·병사 6·수정체력 전부 정확히 복원. 좌표·각도·체력 어긋남 0개.
옛 배열도 계속 읽는다(선생님 화면만 먼저 갱신되는 순간 대비). 빈 목록도 안전.

**아직 확인 안 된 것**: Firebase 안쪽 비용은 여기서 직접 못 쟀다. **추론이다.**
크롬북에서 `브라우저작업` 과 `★프레임분포` 가 실제로 좋아지는지 보고 판단할 것.
좋아지면 다음 후보는 초당 8번 도는 `DOM배치 2.79ms`,
그 다음이 `★그리기 7.16ms`(드로우콜 159개, 콜당 45µs).

### 문자열 전송, 아직 판정 못 함 — 짝비교로 다시 잴 것

배포 후 크롬북 값:

| | 빠름 | 한박자 | 더놓침 | 브라우저작업 |
|---|---|---|---|---|
| 이전(배열) | 70% | 26% | 4% | 9.19ms |
| 이후(문자열) | 80% | 10% | **10%** | **13.00ms** |

**엇갈린다.** 한박자놓침은 26→10% 로 줄었는데 더놓침이 4→10% 로 늘었고,
줄어야 할 브라우저작업이 9.19 → 13.00ms 로 **늘었다.**
게다가 이전 판은 늑대24·5일차 밤이었고 이번 판의 조건은 기록이 없다.
**조건이 다르면 이 비교는 아무 뜻이 없다.**

→ `Shift+8` 을 넣었다. 늑대 상태 포장 방식을 그 자리에서 바꾼다.
   **문자열(3칸) ↔ 옛 배열(206칸)** 을 같은 늑대 수에서 번갈아 누르며
   `브라우저작업` 을 보면 답이 나온다. 순서대로 재면 늑대가 늘어서 못 가른다는 걸
   이미 여러 번 겪었다.
   **문자열이 안 나으면 되돌린다.** 추론으로 넣은 것이라 실측이 아니면 남길 이유가 없다.

## 2026-08-28 밤 — Firebase 가 프레임의 40% 를 먹는다

크롬북 짝비교(Shift+7, 같은 자리에서 껐다 켜기):

```
브라우저작업   켜짐 15.23ms  →  꺼짐 7.30ms      차이 7.93ms
```

**프레임 20ms 중 7.93ms 가 Firebase 다.** 지금까지 찾은 것 중 압도적으로 크다.
(비교: ★그리기 7.16 / DOM배치 2.79 / 시뮬 1.18 / 늑대 0.87)

**포장 방식은 범인이 아니다 — 되돌렸다.**
숫자 배열을 문자열 하나로 묶어 칸을 206개 → 3개로 줄여 봤지만
Shift+8 짝비교에서 **차이가 없었다.** 추론으로 넣은 것이라 되돌렸다.
→ 비용은 **보내는 데이터의 크기가 아니라 `.set()` 을 부르는 횟수 자체**에 붙는다.

지금 초당 몇 번 부르나:
```
myRef.set        6회/초   (내 위치)
sim.set          7회/초   (늑대·병사 전체)   ← host 만
netPC            ~1회/초
netMeta          1회/초
                ─────
                 약 14회/초
```
프레임 분포에서 `한박자놓침 26%` 였던 것과 초당 14회가 얼추 맞아떨어진다
(50fps 기준 28%). 한 번 부를 때마다 프레임 하나를 걷어차는 모양이다.

**다음에 할 일 — `Shift+8` 로 전송 횟수를 반으로 줄여 짝비교.**
초당 13회(위치6+늑대7) ↔ 6회(각 3회). 같은 늑대 수에서 번갈아 누르며 브라우저작업을 본다.
- **비례해서 줄면** → 호출 횟수가 범인 확정
- **안 줄면** → 횟수가 아니라 다른 것. 브라우저작업 안을 더 쪼개야 한다

횟수가 범인으로 확정되면, 부드러움을 잃지 않고 줄이는 길이 있다:
**두 번 부르는 걸 한 번으로 합치기** (`net.update({['p/'+uid]:…, sim:…})`).
갱신 빈도는 그대로 두고 호출만 절반이 된다.
그리고 **host 가 자기가 보낸 `sim` 을 자기가 다시 받고 있다**(`on('value')` 등록해두고 무시).
그 리스너를 host 에선 안 걸면 Firebase 가 하는 일이 준다. 둘 다 아직 안 재봤다.

## 2026-08-28 — 범인: 수정이 공격받을 때 HUD 가 매번 DOM 을 다시 쓴다

선생님 관찰: **"수정 공격당할 때 프레임이 많이 떨어져."** 그게 맞았다.

같은 밤, 16초 차이로 찍은 두 장:

| | 수정 200/200 | 수정 39/200 (공격 중) |
|---|---|---|
| FPS | **54** | **38** |
| 늑대 / 건물 / 병사 | 24 / 0 / 0 | 23 / 0 / 0 |
| 드로우콜 / 삼각형 | 183 / 167K | 181 / **167K** |
| 메모리 | 14MB, 0.0MB/초 | 14MB, 0.0MB/초 |
| 브라우저작업 | 8.78ms | **15.48ms** |
| ★그리기 | 7.24ms | 9.04ms |
| DOM배치 | 2.26ms | 3.07ms |

**아무것도 안 쌓였고 그리는 양도 같은데 느려졌다.** ("뭔가 누적된다" 가설은 기각)
그리고 무너진 상태의 스윕에서 **화면그리기를 통째로 꺼도 +1.15ms 뿐**이었다 → GPU 아님.
반면 **게임로직을 끄면 +17.85ms**. 그 대부분이 구간별에 안 잡히고 브라우저작업에 있었다.

원인: `paintHUD` 는 초당 8번 도는데 **값이 안 바뀌어도 매번 DOM 에 다시 썼다.**
수정이 가득할 땐 값이 그대로라 브라우저가 일을 건너뛴다.
공격받으면 `cFill.style.width` · `cNum.textContent` 가 매번 바뀌고,
특히 `cFill.style.background` 는 그라디언트 문자열이라 같은 값을 넣어도 다시 해석·칠한다.
그 일은 rAF 콜백이 끝난 뒤에 벌어지므로 구간별에는 안 잡힌다.
**하단 바(`paintBar`)에서 이미 겪은 것과 같은 종류다.**

고침: 바뀔 때만 쓴다(`setTxt`/`setSty` + `hudPrev`). 막대 너비는 0.1% 로 끊는다.
검사: 가만히 있을 때 80번 호출에 **DOM 쓰기 0회**(예전 방식이면 약 960회),
공격 중엔 158회(진짜 바뀌는 값만). 표시 오류 0개, 색 임계 4단계 정상.

**확인됨** — 고친 뒤 크롬북에서 수정이 공격받아도 **주로 38 위**, 가끔 33~34.
고치기 전에는 공격 시작과 함께 38 로 떨어져 계속 내려갔다. 바닥이 올라가고 급락이 줄었다.
짝비교는 안 했으므로 정확한 ms 는 모른다. 개선은 있으나 극적이지는 않다.

# 4차 패치 — 겉모습 갈아엎기 (2026-08-29)

> "타워, 벽, 자원, 배럭, 병정 디자인이 왜이렇게 눈에 안차지 좀더 멋지게 만들어줄 수 없어?

기능은 안 건드렸다. **보이는 것만 전부 다시 만들었다.**

## 왜 어설퍼 보였는지 — 먼저 원인부터

세 가지였다.

1. **기울어진 면이 하나도 없었다.** 지붕을 계단식으로 쌓아 놨는데,
   계단 지붕은 아무리 잘 쌓아도 "지붕처럼 보이는 계단"이지 지붕이 아니다.
2. **실루엣이 밋밋했다.** 처마도 받침도 없이 네모 기둥이라
   멀리서 보면 그냥 상자였다.
3. **재질 대비가 없었다.** 나무 건물이 전부 같은 갈색 하나였다.
   골조는 짙고 벽은 밝아야 "지어 놓은 집"으로 보인다.

셋 다 고쳤다.

## 1. 블록에 '옆으로 기울이기'를 열었다 — 이게 제일 큰 열쇠

건물 블록 형식이 `[x,y,z,타일,w,h,d,색,ry]` 였다. 여기에 `rz` 를 붙였다.

```js
const [x,y,z,dmg,bw,bh,bd,tint,bry,brz] = arr[i];
if(bry || brz){ _eu.set(0, bry, brz, 'YXZ'); _q.setFromEuler(_eu); } else _q.identity();
```

오일러 순서 `YXZ` 는 **Z 먼저, 그 다음 Y** 로 돈다. 그래서
`rz`(옆으로 눕히기) → `ry`(방향 돌리기) 순으로 먹어서, 어느 면에 붙은
지붕널이든 제대로 기울어진다. 비용은 0이다 — 어차피 인스턴스마다
행렬을 만들고 있었다.

> 한 번 틀렸다. 처음엔 `ry` 만으로 지붕을 기울이려 했는데,
> 지붕널은 **용마루 축을 중심으로 굴러야** 하지 세로축으로 돌면 안 된다.
> 그래서 형식에 `rz` 를 새로 냈다.

## 2. 새로 만든 조립 도구

| 이름 | 하는 일 |
|---|---|
| `R` | 회전까지 주는 날블록 |
| `ROOF` | **진짜 맞배지붕** — 널판을 양쪽에서 기울여 맞댄다 |
| `PLINTH` | 바닥 굽 — 건물이 땅에 '앉아' 보인다 |
| `CORBEL` | 처마 받침 — 위층이 아래층보다 튀어나오게 |
| `PANEL` | **하프팀버 벽** — 회벽 + 짙은 나무 골조 + X 가새 |

`PANEL` 이 새 건물들의 얼굴이다. 회벽(밝음)과 골조목(짙음)의 대비가
"어설픈 갈색 상자" 를 "지어 놓은 집" 으로 바꿔 놨다.

## 3. 등급마다 재료가 바뀐다

| 등급 | 화살탑 | 배럭 | 벽 |
|---|---|---|---|
| Lv1–2 | 하프팀버 망루 · 초가 맞배지붕 · X 가새 | 통나무 오두막 · 초가 | 통나무 방책 (끝을 뾰족하게 깎음) |
| Lv3–4 | 돌탑 · 붉은 기와 · 나무 회랑 | 돌집 · 기와 · 굴뚝 | 성벽 · 굽 · 띠돌 · 화살구멍 · 총안 |
| Lv5–6 | 성탑 · 넓은 슬레이트 · 금띠 · 내쌓기 발코니 · 첨탑 | 성 · 총안 · 슬레이트 마법사 탑 | 금띠 · 깃발 · 유리창 |

애들이 강화할 때마다 **재료가 통째로 바뀌는 게 보인다.**
나무 → 돌 → 성. Lv1 문 앞과 Lv6 문 앞은 아예 다른 마을처럼 보인다.

얼음탑은 허리를 잘록하게 깎아 **보석 심장이 드러나게** 했고,
얼음 조각들이 사방으로 비스듬히 뻗는다 (회전이 열려서 가능해졌다).

## 4. 자원 · 병정

- **나무** — 밑동이 넓고 뿌리가 드러난다. 줄기는 위로 갈수록 가늘어지고,
  가지 둘이 비스듬히 뻗는다. 잎은 네모가 아니라 **반지름이 다른 4겹 둥근 관**.
- **바위** — 같은 크기 자갈 무더기였던 걸, 큰 덩어리 하나에
  작은 것들이 붙고 **꼭대기에 이끼**가 낀 모양으로.
- **금** — 어두운 암반에 **밝은 금맥**이 박히게. 대비가 세서 멀리서도 눈에 띈다.
- **병정** — 몸통이 `1.16 너비 × 1.02 높이` 였다. **가로가 더 길었다.**
  그래서 판자처럼 보였던 것이다. `0.94 × 1.22` 로 세우고 크기도 키웠다.
  어깨 갑옷 · 모둠색 망토 · 투구 가리개를 붙였다.

> 두 번 틀렸다. (1) 바위 텍스처에 중간 회색을 입혔더니 **석탄 덩어리**가 됐다.
> 재질 색은 텍스처에 **곱해진다** — 밝게는 못 하고 어둡게만 된다. 색을 뺐다.
> (2) 병정 갑옷에 벽돌 타일을 썼더니 **가슴에 벽돌담**이 생겼다. 돌 타일로 바꿨다.

## 5. 화려해졌는데 드로우콜은 오히려 줄었다

건물이 훨씬 복잡해졌으니 그냥 두면 느려진다. 두 가지로 갚았다.

**(가) 타일을 새로 굽지 않았다.** 지붕 타일을 **거의 흰색**으로 구워 두면
색만 물들여서 붉은 기와도 되고 슬레이트도 된다. 그래서 새 재질이라곤
`cutStone` **하나뿐**이다.

```js
bake(T.roofRed, tileRoof([238,234,230], 131));   // 물들이면 기와도 슬레이트도 된다
const TT = { timber:0xcaa070, plaster:0xf4ecd8, clay:0xc0563f,
             slate:0x7f8ea8, iron:0xb4c0d8, gem:0xffffff };
```

**(나) 잎 뱅크 셋을 하나로 합쳤다.** 이게 결정타였다.
둥근 잎을 만들면서 밝은 잎 / 중간 잎 / 기본 잎을 **재질 셋**으로 나눴는데,
셋이 각각 16조각으로 쪼개져 **드로우콜 48개**를 먹고 있었다.
지오메트리도 텍스처도 똑같고 **색만 달랐다.** 색을 인스턴스로 내렸다.

```js
if(col && !b.cols) b.cols = new Array(b.ms.length).fill(0xffffff);
...
if(b.cols){ for(let j=0;j<idxs.length;j++) _col.setHex(b.cols[idxs[j]]), im.setColorAt(j,_col);
            im.instanceColor.needsUpdate = true; }
```

48조각 → **16조각.** three.js 가 instanceColor 를 재질 색에 곱해 주므로
화면은 완전히 똑같다 (검사로 세 톤이 다 살아 있는 것 확인).
장식용 나무도 210그루 → 165그루로 줄였다.

| 시점 | 갈아엎기 전 | 갈아엎은 뒤 |

**건물이 훨씬 화려해졌는데 드로우콜은 오히려 줄었다.**
교실 크롬북(Mali-G72)에서 드로우콜 1개가 60us 니까, 넓은 시야에서 약 0.8ms 이득이다.

# 5차 패치 — 화면 인터페이스 정돈 (2026-08-29)

> "이제 전체적인 화면 인터페이스를 세련되게 개선하자"

먼저 **실제 화면을 찍어 놓고** 뭐가 문제인지부터 봤다. 예쁘고 안 예쁘고 이전에
**깨져 있는 자리가 여럿이었다.**

## 찾아낸 문제 (다섯 가지, 다 실제 버그)

1. **아래 핫바의 값 표시가 잘려 나갔다.** 값이 세 개인 건물(배럭 🪵14 🪨11 ✨4)은
   한 줄에 안 들어가 두 줄로 접혔는데, 칸 높이가 한 줄치라 `overflow:hidden` 에
   ✨ 가 통째로 잘렸다. 애들이 배럭 값을 볼 수가 없었다.
2. **조작 안내가 핫바 밑에 깔려** 글자끼리 겹쳤다.
3. **태블릿에서 핫바가 조이스틱과 큰 버튼을 덮었다.** 손가락이 핫바에 먼저 닿아서
   왼쪽 아래로 이동도, 오른쪽 아래로 캐기도 안 되는 자리가 생겼다. 정작 목표 기기다.
4. **보스 바가 수정 바를 가렸다.** 보스가 나온 밤에 수정이 얼마 남았는지가 안 보였다.
5. **보스 패널이 통째로 두 개였다** (같은 id 로 `bossWrap`·`bFill`·`bNum` 이 중복).
   `부하 N마리 · 수정까지 N칸` 줄은 **숨어 있는 쪽**에 쓰이고 있어서
   **여태 아무도 못 봤다.**

그리고 방 코드 칸의 자간 3px 이 안내 글씨에까지 먹어서 `선 생 님 이  알 려 준` 으로 깨져 있었다.

## 고친 것

### 1. 아래를 트레이 하나로 합쳤다

도구줄과 건물줄이 **따로 떠 있는 상자 둘**이라 서로 겹쳐 보였다.
`#dock` 하나로 묶고 가운데 칸막이를 넣었다. 겹칠 수가 없어졌다.

값 표시는 **두 칸짜리 격자**로 못 박았다. 그림문자가 넓어서 어느 글자 크기로도
셋을 한 줄에 못 넣는다 — 억지로 밀지 말고 `2개 + 1개(가운데)` 로 늘 똑같이
접히게 하고, 칸 높이를 두 줄만큼 미리 잡았다. 다섯 칸의 글자 높이가 다 맞는다.

**태블릿에서는 도구줄을 건물줄 위로 올려** 트레이를 좁게 만든다.
그러면 왼쪽 조이스틱과 오른쪽 큰 버튼 사이에 딱 들어간다.

### 2. 색을 다시 골랐다

칙칙한 군용 녹회색 → **따뜻한 남보라 + 크림 + 꿀색.**
하늘도 잔디도 밝은 화면이라 어두운 판이 맞지만, 색이 탁하면 재미가 없다.
모서리를 둥글리고 그림자를 부드럽게 했다. 3학년이 볼 화면이다.

- **자원** — 나무/돌/금이 각자 제 색 알약을 갖는다. 늘면 숫자가 통 튄다.
- **시간** — `150` 이라고만 뜨던 걸 `2:30` 으로. 20초 밑이면 분홍으로 뛴다.
- **알림 줄** — 하늘 위에서 글자가 안 읽혀서 **알약 배경**을 깔고 왼쪽에 꿀색 띠를 넣었다.
  일곱 줄까지 쌓이던 걸 다섯 줄로.
- **조준선** — 가운데가 트인 십자 + 점. **캘 수 있는 자리·고칠 수 있는 건물 앞에서
  꿀색으로 커진다.** "여기 눌러도 되나?" 를 안 헷갈린다.
  (가짜요소는 둘뿐이라, 막대에 '가운데만 투명한 그라디언트'를 먹여 팔 넷을 만들었다)
- **조작 안내** — 트레이 위로 올리고 **30초 뒤 스르르 사라진다.** 한 번 읽으면 된다.

### 3. 도움말을 글 벽에서 카드로

한 화면을 꽉 채운 줄글이었다. 3학년이 읽을 리가 없다.
**아이콘 붙은 줄**로 쪼개고 `낮·밤 / 짓기 / 강화 / 나와 친구 / 늑대 / 지을 수 있는 것`
으로 묶었다. 시간·값은 알약으로 뽑아냈다. `Lv.3까지` 라고 남아 있던 옛 문구도 고쳤다.

### 4. 시작 화면

- **모둠 단추에 고르기 전부터 색이 보인다.** 애들은 번호가 아니라 색으로 기억한다.
- 카드 위에 다섯 모둠 색 띠를 하나 얹었다.
- 방 코드 안내 글씨 깨짐 수정.

## 성능 — 이번엔 조심할 게 있었다

`backdrop-filter`(뒤 배경 흐리기)를 넣었다가 **뺐다.** 예뻐 보이지만 합성기가
매 프레임 프레임버퍼를 읽어다 흐려야 해서, 교실 크롬북의 타일 GPU 에서 아주 비싸다.
패널이 이미 90% 불투명이라 흐림이 **보이지도 않았다.** 값 알약도 벗겼다.

| | 예전 UI | 새 UI |
|---|---|---|
| HUD 배치·칠하기 (최악: 값이 매 프레임 바뀔 때) | 0.19 ms | **0.22 ms** |

실제로는 `paintHUD` 가 초당 8번 돌고 대부분의 값은 안 바뀌므로,
프레임당으로 환산하면 무시할 수준이다. **값이 안 바뀌면 DOM 을 0건 건드린다**는
기존 규칙도 그대로다 (100번 칠해도 변경 0건 — 검사로 확인).

# 6차 패치 — 망루·모둠 현황·교실 사고 막기 (2026-08-30)

> "1,2는 신경쓰지말고 나머지는 고쳐줘. 특히 6번,7번 아주 아주 아주 신경써서 잘 고쳐줘."

## ⑦ 성문 망루에 올라가기 — 제일 공들인 것

밤에 애들이 할 일이 '구경 + 돌 던지기' 뿐이라 얕았다.
**문 옆 계단으로 망루에 올라가 내려다보며 던지는** 자리를 만들었다.

### 왜 이게 안전한 방법인지 — 코드를 먼저 읽었다

```js
function walkable(x,z){
  const t = terrH[gi(x,z)];        // ★ terrH 만 본다. bldH 는 아예 안 본다.
  return t >= GY && t <= GY+1;
}
```

늑대 길찾기는 **`terrH` 만** 읽는다. 그래서 **`bldH` 로 만든 계단은 늑대에게 보이지 않는다.**
`terrH` 를 건드렸다면 늑대가 길을 잃거나 통로가 막혔을 자리다.
플레이어 발밑은 `solidTop = max(terrH, bldH)` 이라 계단 위를 걷는다.

또 하나 — **`terrH` 는 정수 배열**이라 한 칸이 1 이상씩 오르는데,
올라갈 수 있는 턱(`STEP`)은 **0.68** 이다. 정수 계단은 애초에 못 올라간다.
`bldH` 는 실수라 0.55씩 올릴 수 있다. 이 두 가지가 설계를 정했다.

### 세 번 고쳐 잡은 것

| 틀린 것 | 어떻게 드러났나 | 고침 |
|---|---|---|
| `bldH` 에 **상대 높이**를 넣었다 | 계단이 아예 없는 것처럼 몸이 통과 | `bldH` 는 절대 y — `GY + h` 로 |
| 발판 높이를 6.6 으로 **못 박았다** | 산기슭이 3~12로 가팔라 발판이 바위에 파묻힘 | **그 자리 산 높이를 재서** 스스로 정하게 |
| 발판을 문에 **딱 붙였다** | 망루 몸통과 번호판 사이에 끼어 벽만 보임 | 마을 쪽으로 물려 **비스듬히 내려다보게** |

### 지금 모습

- 문 양옆으로 **돌계단**이 오르고, 위에 **총안 달린 발판**이 있다 (모둠 깃발·횃불)

## ① 꾸미기 — 모자·안경·옷 + 시작 화면에서 진짜 3D 미리보기

모자 5가지뿐이었던 걸 **모자 9 · 안경 7 · 옷 7** 로 늘렸다.
조각 표(`HATS`/`GLASSES`/`CLOTHES`)만 늘리면 되게 해 놨다 — 새 아이템 하나에
`[앞f, 위u, 옆sd, 가로, 세로, 깊이, 색]` 몇 줄이면 끝난다.

> **새 옷을 붙일 때 알아야 하는 기준점** (한 번 몰라서 볼터치를 머리 속에 파묻었다)
> 머리 f 0.68 u 1.06 (앞면 f 0.99) · 눈 f 1.02 u 1.13 ·
> 몸통 f 0 u 0.56 (앞면 f 0.47) · **등털 f −0.05 u 0.98, 옆 ±0.54, 뒤 −0.63, 위 1.32**

천 텍스처에 색·크기만 바꿔 끼운다. 아무도 아무것도 안 걸치면 통째로 숨긴다.

본 게임 양을 그대로 못 가져다 쓰는 이유: 인스턴스 메시는 **렌더러 둘이 같은 버퍼의

아이가 고르는 건 그것뿐이라 여기서 본 착장과 게임 속 모습이 어긋나지 않는다.

## ② 죽으면 3인칭 — 그리고 진짜 버그였던 것

> "죽었을 때 화면이 좀 이상해. 움직이지는 않은데 점프가 돼."

코드를 보니 진짜였다. `updPlayer` 가 **이동만 막고 점프는 안 막고 있었다**:

```js
if(!PL.down){ ...WASD... }          // 이동은 막았는데
if(wantJump && PL.ground){ ... }    // ← 점프는 그대로 실행된다
```

거기에 카메라는 눈높이만 0.42 로 낮춘 1인칭이라 **누운 얼굴이 땅에 박혀** 흙바닥만 보였다.
무슨 일이 벌어지는지 하나도 안 보이니 "화면이 깨졌다"고 느낀 게 맞다.

- 점프 차단 (`&& !PL.down`)
- **내 시체 뒤 위쪽 4.6칸으로 물러난다.** 벽·산에 파고들지 않게 막히기 직전까지만 물러난다
- 쓰러지는 순간 살짝 내려다보게 시선을 맞춰 준다 (내 몸이 화면에 들어오게)
- **3인칭이니 내 몸도 그려야 한다** — 평소엔 1인칭이라 안 그리던 것을 `meSheep` 으로 추가

## ③ 상인 — 무기 6종·방어구 5종·물약 4종

**수정 옆 좌판에 낮에만 선다.** 가까이 가면 안내가 뜨고 `B`(태블릿은 안내를 누르기)로 열린다.
밤에 살 수 있으면 위험할 때 돈으로 때우게 되어 '낮에 준비한다'는 리듬이 사라진다.

| 무기 | 값 | 한 방 | 간격 | 사거리 | 총알 |
|---|---|---|---|---|---|
| 🪨 맨손 돌 | 공짜 | 17+날짜×4.4 | 1.00 | 11.5 | — |
| 🎯 나무 새총 | 🪵35 | 30 | 0.75 | 15 | — |
| 🔫 돌 화승총 | 🪵40 🪨35 | 62 | 1.10 | 18 | 1 |
| 🔩 쇠 소총 | 🪵20 🪨70 ✨8 | 105 | 0.85 | 22 | 1 |
| 💨 연발총 | 🪵60 🪨90 ✨16 | 60 | 0.42 | 19 | 1 |
| 🏆 금빛 저격총 | 🪨80 ✨34 | 300 | 1.70 | **34** | 2 |
| 💎 수정 광선총 | 🪵80 🪨80 ✨60 | 200 | 0.85 | 26 | 2 |

무기 힘은 **하루 +14%** 로 자란다. 안 그러면 후반 늑대(체력 1.85배) 앞에서
비싸게 산 총이 이틀 만에 장난감이 된다.
**총알은 금 1개에 6발.** 금 산출을 통째로 2배로 올렸다(광맥 4→8, 아침 보상·상자·보스도 2배).

방어구는 **물린 피해를 % 로 줄인다**(12/24/38/52/64). 최소 1은 남긴다 —
"갑옷 사면 아예 안 아파요" 가 되면 밤이 무섭지 않다.
물약은 사 두었다가 **6·7·8·9** 로 마신다(회복 +45 / 걸음 +35% / 공격 +60% / 방어 +25, 40초).

> **총알이 떨어지면 막지 않고 조용히 맨손 돌로 떨어진다.** 9살한테
> "총알이 없습니다" 하고 아무 일도 안 일어나면 그냥 손을 놓아 버린다.
> 대신 그 밤에 한 번은 알려 준다.

**자원은 모둠 공용이다.** 총 하나를 사려면 모둠이 상의해야 한다 — 그게 이 게임의 핵심이다.

화면 왼쪽 위, 체력 바 밑에 **지금 든 무기 그림 + 공격력 / 입은 갑옷 그림 + 방어력 / 총알**이 뜬다.
고정된 ⚔️ 대신 **실제 아이템 그림**을 쓰는 이유: 뭘 들었는지 확인할 곳이 여기밖에 없다.

## ④ 데미지 숫자 · 크리티컬 · 늑대 체력바

늑대가 조용히 사라져서 **탑이 일하고 있는지 아닌지를 애들이 몰랐다.**

- 탑·병정·내 무기가 때리면 **얼마나 아팠는지 숫자가 뜬다**
- **크리티컬 14% · 2배** — 노랗고 크게, 뒤에 `!` 가 붙는다
- 늑대 머리 위 **체력 막대** (초록→노랑→빨강, 보스는 넓게)

숫자는 **3D 스프라이트가 아니라 화면 위에 얹은 글자 판**이다. 스프라이트로 만들면
숫자 하나에 드로우콜이 하나씩 붙는다. 칸 18개를 돌려 쓰고, 매 프레임 건드리는 건
`transform` 과 `opacity` 뿐이라 배치 계산이 다시 안 돈다 → **18개 가득 떠도 0.0055ms**.

체력 막대는 **인스턴스 두 벌(바탕·채움)** 이라 몇 마리가 있든 그리기가 두 번이다.
늑대가 없으면 통째로 숨긴다(안 숨기면 개수가 0이어도 그리기가 돈다 — 실측으로 잡았다).

> **손님 화면의 숫자는 '흉내'다.** 피해는 호스트만 준다. 늑대 체력은 통신에
> **백분율로만** 오기 때문에 실제로 깎인 값을 알 방법이 없다. 그래서 같은 표로
> 같은 값을 다시 계산해서 띄운다(`clientTowerFx`/`clientSoldierFx`).
> **내가 쏜 것만은 진짜다** — 무기도 크리티컬도 내 것이라, 피해량을 내가 계산해서
> `td` 칸에 실어 보낸다. 통신 횟수는 한 번도 안 늘었다.

## ⑤ 공격 속도를 반으로, 한 방을 1.7배로

0.4초마다 자잘하게 때리면 뜬 숫자가 서로 겹쳐 아무것도 안 읽힌다.
화살탑 `0.70→1.40초 / 13→22`, 얼음탑 `1.10→2.20초 / 8→14`, 병정 `0.80→1.60초`,
돌 던지기 `0.5→1.0초`. 얼음탑은 간격이 2배가 됐으니 **어는 시간도 같이 늘렸다**(1.6→2.6초).
안 그러면 얼자마자 풀린다.

크리티컬까지 넣으면 실제 화력은 예전의 **0.92배** — 요청대로 조금 어려워졌다.

원인은 6차 패치 때 물기 판정만 고치고 **쫓는 판정은 안 고친 것**이었다.
쫓기는 가로 거리만 봤다. 이제 둘 다 같은 `SHEEP_REACH_Y = 2.2` 를 쓴다 —
"쫓아오는데 안 물린다" 나 "안 쫓는데 물린다" 가 원리적으로 안 생긴다.
내 벽(1.4) 위는 여전히 쫓고, 망루 발판(5.5~7)은 아예 목표로 안 잡는다.

- **양을 쫓을 땐 걸음이 1.42배.** 다만 양의 달리기(5.4)보다는 느리게 막아 뒀다(5.0).
  9살이 아예 못 도망치면 게임이 아니라 벌이다
- **수정을 더 노린다** — 건물부터 노리는 비율 0.35→0.24,
  거기에 **한 마리가 건물을 물고 늘어질 수 있는 시간 11초**를 줬다.
  다 쓰면 그 늑대는 수정만 노린다. 이게 없으면 벽이 두꺼운 밤에 늑대 떼가
  마당 밖에서 벽만 갉다가 밤이 끝났다 — 수정은 멀쩡한데 아무 일도 안 일어나서 지루했다

## ⑦ 밸런스 — 재 보고 정했다

낮 **150→140초**. 늑대 **체력 1.85배 · 건물 피해 2배**.

요청은 "피 두 배 데미지 두 배" 였는데, **2.0/2.0 은 재 보니 못 이기는 밤이 나왔다.**
그대로 넣지 않고 세 가지를 갈랐다:

- **수정 깎는 힘은 따로 1.4배** — 2배로 하면 늑대를 55마리 중 53마리 잡고도
  새어 든 두 마리가 20초 만에 수정을 다 갉는다. "한 마리라도 새면 끝"이 되어
  막아 내는 재미가 아니라 운이 된다
- **보스 체력도 따로 1.35배** — 잡몹과 똑같이 2배로 했더니 마지막 밤 늑대왕이 34000이 되어
  열 명이 저격총을 쏴도 안 죽었다
- **잡몹 체력 1.85배** — 2.0 에서는 15일차가 세 판 중 한 판만 버텼다

측정은 `bal4.mjs` 로 했다. 헤드리스로 밤을 통째로 돌리되,
**애들이 실제로 하는 세 가지**를 모형에 넣어야 정직한 값이 나온다 —
총 쏘기 · 밤에 수리하기 · **위험한 입구로 달려가기**.
(마지막 것을 빼면 15일차가 0/3 으로 나온다. 게임이 직접
"🚨 3모둠 쪽에 늑대 6마리! 가까운 친구들 도와주러 가요" 라고 알려 주는데,
제자리에 못 박아 두고 재면 그 알림이 없는 셈으로 재는 것이다.)

| 반이 얼마나 움직이나 | 12일차 | 15일차 |
|---|---|---|
| 탑만 (아무도 안 움직임) | 1/3 | 0/3 |
| 수리만 8명 | — | 0/3 |
| 총 4명 + 수리 4명 (반만 참여) | 3/3 | 1/3 |
| **총 8명 + 수리 8명 (보통)** | **3/3** | **3/3** (남은 수정 125·200·200) |
| 총 14명 + 수리 10명 | — | 3/3 여유 |

**즉 "마지막 밤은 반 전체가 움직여야 이긴다"** 가 됐다. 그게 이 게임이 하려는 것이다.
너무 어려우면 `BAL.hpMul` 을 1.7 로 낮추거나 선생님 패널의 **늑대 세기를 0.9** 로 두면 된다.

> **뱅크 하나는 모양(geo)이 첫 번째 넣은 것으로 고정된다.**
> 상인 좌판을 열쇠 하나('shop')에 판자·통나무·천·금 네 모양을 섞어 넣었더니
> 전부 판자로 그려져서 통나무 덩어리가 됐다. 나무 것은 판자 하나로,
> 나머지는 천 하나로 갈라 **그리기 두 번**으로 끝냈다.
>
> **세계 좌표의 각도 a 는 (cos a, sin a) 인데, three.js 의 Y축 회전 θ 는
> 제자리 +Z 를 (sin θ, cos θ) 로 보낸다.** 그래서 바깥쪽을 보게 하려면 `θ = π/2 − a` 다.
> `a + π/2` 로 썼다가 좌판이 뒤집혀서, 애들이 다가오는 쪽에서는 상인 뒤통수만 보였다.
> 조각의 **놓이는 자리(dx·dz)도 같이 돌려야** 한다 — 안 그러면 차양만 돌고 기둥은 제자리에 남는다.

# 8차 패치 — 총 장착(T)·FPS 조준·타격감·가방(I)

7차에서 총을 넣었더니 "우클릭으로 던지는 돌"과 다를 게 없다는 이야기가 나왔다.
세 가지를 고쳤다: **모드**, **타격감**, **가방**.

## ① T 로 총을 장착하고, 왼쪽 클릭으로 쏜다

우클릭 사격은 "총을 들었다"는 느낌이 없었다. 총을 사고도 계속 곡괭이를 든 것 같았다.

- **T** — 총 장착/해제. 우클릭도 같은 일을 한다(둘 다 되게 뒀다)
- 장착하면 **왼쪽 클릭이 곧 사격**이고, 누르고 있으면 연사된다(연발총)
- 장착한 동안은 **캐기·짓기가 잠긴다.** 안 잠그면 늑대를 쏘려다 발밑에 벽을 짓는다
- **아침이 오면 저절로 풀린다** — 공격 모드인 줄 모르고 "왜 안 캐져요" 하는 일을 막는다
- 태블릿엔 T 키가 없다. 오른쪽 아래 전용 버튼이 곧 방아쇠이고,
  **지금 든 무기 그림으로 바뀐다**(🪨던지기 → 🏆쏘기)

## ② 진짜로 겨눠야 맞는다

예전 조준은 **앞쪽 57도 원뿔 안이면 다 맞았고, 위아래는 아예 안 봤다** — 하늘을 보고 쏴도 맞았다.
조준이랄 게 없었던 셈이다.

이제 카메라가 보는 **조준선 둘레의 통** 안에 들어와야 맞는다.

```js
const along = dx*f.x + dy*f.y + dz*f.z;    // 조준선을 따라 얼마나 앞인가
const perp  = |(dx,dy,dz) − f*along|;       // 조준선에서 얼마나 벗어났나
if(perp > aimR + along*0.05) continue;      // 거리에 비례해 조금씩 넓어진다
```

너그러움(`aimR`)은 무기마다 다르다 — 맨손 돌 2.6칸, 연발총 1.7, 쇠 소총 1.5, **저격총 1.1**.
저격총은 빡빡한 대신 사거리 34칸에 한 방이 제일 세다.
조준점 한가운데에 늑대가 들어오면 **빨갛게** 바뀌고, 맞으면 ✕ 로 번쩍인다(크리는 노랗게 크게).

## ③ 타격감 — 세 번 갈아엎었다

**첫 번째: 총알 한 알이 날아가게.** 안 보였다.
1인칭에서는 총알이 내가 보는 방향 그대로 가므로, 화면에서는 조준점 위의 점 하나로 뭉개진다.

**두 번째: 총구에서 표적까지 빛줄기를 한 번에 그리고 굵기를 줄이며 지운다.**
이건 보인다 — 총구가 조준선에서 옆·아래로 빠져 있으니 줄기가 화면을 비스듬히 가로지른다.
다만 **총구를 눈앞 0.85칸에 뒀더니 줄기의 '가까운 끝'이 부풀어** 화면 오른쪽 아래가
색 덩어리가 됐다. 1.7칸 앞·오른쪽 0.5칸·아래 0.3칸으로 빼서 잡았다.

**세 번째: 총구 화염을 손에 든 모형에 붙였다가 뺐다.**
카메라에서 0.34칸밖에 안 떨어져서, 조금만 키워도 **화면 절반을 덮는 금덩어리**가 됐다.
지금은 세계 좌표에 짧고 굵은 빛줄기 한 토막으로 놓는다 — 크기가 예측 가능하고,
예광탄과 같은 메시를 쓰므로 **그리기가 안 는다.**

여기에:
- **반동** — 총구가 위로 들리고 몸 쪽으로 밀린다(0.14초에 걸쳐 돌아온다). 무기마다 세기가 다르다
- **화면 흔들림** — 반동에 비례해서
- **명중 불꽃** 두 겹(무기 색 + 흰 불티)
- **총 소리** 세 가지 — `gun`(짧고 날카로운 파열음), `boom`(저격총), `laser`(광선총)
- 무기마다 **빛줄기 색**이 다르다 (금빛 / 주황 / 하늘빛)

> 손에 든 총도 두 번 고쳤다. 도구와 같은 크기·각도로 뒀더니 **화면 절반을 덮는 통나무**가 됐고
> (총은 곡괭이의 두 배 길이다), 낮춰 놨더니 **아래 트레이에 완전히 가려**졌다.
> 화면에 찍어 보고 크기 0.46·자리 (0.26, −0.20, −0.62) 로 잡았다.

## ④ 가방 (I)

산 물건이 **자동으로 끼워지고 그게 끝**이라, 상황에 맞게 바꿔 쓸 수가 없었다
(망루에 올라갈 땐 저격총, 문 앞에선 연발총).

- **I** 또는 오른쪽 위 🎒 버튼으로 열린다
- 무기·방어구를 눌러 **장착**, 다시 누르면 **푼다**(맨손 돌 / 털만 믿기로)
- 물약은 눌러서 바로 마신다
- 맨 위에 지금 공격력·방어력·총알

> **이걸 하면서 자료 구조를 갈랐다.** 예전엔 `KIT.wpn` 숫자 하나가
> "가지고 있는가"와 "들고 있는가"를 겸했다(`buyWeapon` 이 `KIT.wpn >= i` 로 보유를 판단).
> 낮은 무기로 바꿔 끼는 순간 비싸게 산 무기가 **없는 것이 된다.**
> `ownW`/`ownA`(가짐)와 `wpn`/`arm`(듦)으로 나눴다.

## 검사

t3 13 / t4 25 / t6 31 / t7 26 / t8 42 / t9 28 / t10 67 / **t11 34** = **266항목 전부 통과**

t11 이 이번 패치 전용이다. 특히:

- 총을 들면 **10초 동안 눌러도 벽이 안 지어지나**, 풀면 지어지나
- 아침에 저절로 풀리나
- **옆으로 6칸·위로 7칸 벗어난 늑대가 안 잡히나**(예전엔 둘 다 맞았다)
- 사거리 밖이 안 잡히나 / 저격총으로 바꾸면 잡히나
- **같은 자리에서 맨손 돌은 맞고 저격총은 빗나가나**(무기별 너그러움)
- 쏘면 빛줄기 두 토막(줄기+화염)이 생기나 / 색이 그 무기 색인가 / 반동이 생기나
- **맨손 돌은 빛줄기가 아니라 던지는 돌인가**
- 가방에 **산 것만** 나오나 / **낮은 무기로 바꿔 껴도 비싼 무기가 사라지지 않나**

## 성능

드로우콜은 7차와 같다(중앙값 83/194/104 — 측정 흔들림 폭 안).
빛줄기는 메시 하나를 돌려 쓰고 **날아가는 것이 없으면 통째로 숨긴다.**
총구 화염도 같은 메시를 쓰므로, 쏘는 동안 늘어나는 그리기는 **1번**이다.

# 9차 손질 — 직접 둘러보고 찾아 고친 것들

여러 화면 크기에서 낮·밤·보스·팝업을 전부 찍어 보고, 눈에 걸리는 것을 잡았다.
새 기능이 아니라 **이미 있던 것이 제대로 안 보이던 것**들이다.

## ① 늑대 체력 막대가 까만 칸으로만 보였다 (버그)

8차에서 넣은 막대가 **한 번도 제대로 보인 적이 없었다.**
바탕과 채움이 같은 자리·같은 거리에 있는데 둘 다 투명이라,
어느 것을 나중에 그릴지가 프레임마다 뒤집혀서 대개 까만 바탕이 이겼다.

```js
HB_BG.renderOrder = 3; HB_FG.renderOrder = 4;   // 순서를 못 박고
setI(HB_FG, n, w.x + rx2*off - fx2, y, ...);    // 채움을 카메라 쪽으로 0.05칸 당긴다
```

이제 초록→노랑→빨강이 제대로 보인다. 막대도 조금 두껍게(0.15→0.17) 했다.

## ② 좁은 화면에서 자원 패널이 수정 바를 덮었다 (버그)

가운데 판은 화면 한가운데에 두고 '96vw 까지' 만 막아 놨는데,
**1024 이하에서는 왼쪽 자원 패널과 오른쪽 날짜·지도가 안쪽으로 밀고 들어왔다.**
교실 크롬북(1024×640)과 태블릿에서 **1모둠 칸이 통째로 가려져 있었다.**

이제 양옆에 '판이 차지하는 폭'만큼 자리를 비워 두고 그 안에서 가운데 정렬한다.
왼쪽 패널 폭과 비워 두는 폭을 **한 곳(`--hudLeftW` / `--hudSide`)에서 같이** 줄인다 —
따로 두면 한쪽만 줄어 다시 겹친다.

검사로 **7가지 화면 크기(1400×860 ~ 760×420, 세로 태블릿 포함)** 에서
가운데 판이 다른 판에 가리지 않고 화면 밖으로도 안 나가는지 본다.

## ③ "지금 뭘 해야 하는지"가 화면 어디에도 없었다

첫날 화면에는 들판만 있었다. 3학년이 처음 들어와서 볼 것이 없다.
아래 트레이 위의 '키 목록'(30초 뒤 사라지던 것)을 **지금 할 일 한 줄**로 바꿨다.

- 처음 25초 — `WASD 이동 · 좌클릭 사용/사격 · T 총 · I 가방 · B 상인 · Space 점프`
- 낮 — `☀️ 나무·돌·금을 캐서 우리 모둠 입구를 막으세요`
- 밤 — `🌙 늑대를 막으세요! 부서진 곳은 🔧수리 · T 로 총 들기`
- 상인 앞 — `🛒 상인이 눈앞에 있어요 — B 를 눌러 무기·물약을 사세요`
- 쓰러짐 — `💫 쓰러졌어요 — 친구가 앞에서 8초 눌러 주면 일어나요`

**태블릿에도 보여 준다.** 반의 절반이 태블릿인데 할 일을 못 보면 안 된다.

> 자리는 숫자로 못 박지 않고 **트레이 높이를 재서** 잡는다(`fitHint`).
> 트레이는 화면 크기·터치 여부에 따라 130~178px 로 달라지는데,
> `bottom:172px` 로 박아 놨더니 1024×768 태블릿에서 트레이를 덮고 있었다.
> 터치에서는 조이스틱과 큰 버튼 사이의 폭만 쓰도록 너비도 같이 잰다.

## ④ 지도에 상인이 없었다

좌판을 **우연히 지나가야만** 발견할 수 있었다.
낮에만 지도에 빨간 차양 + 흰 좌판으로 깜빡인다. 밤에는 문을 닫으므로 사라진다.

## ⑤ 팝업이 잘려 있는데 잘린 줄을 몰랐다

세로가 짧은 교실 크롬북(640px)에서 **끝나고 띄우는 기록판의 아랫부분(순위표)이
통째로 안 보였다.** 스크롤은 되지만 막대가 거의 안 보여서 아무도 몰랐다.

# 10차 — 총 여섯 자루를 따로 만들고, 떠 있던 손을 붙였다

> "총을 들 때 손이 둥둥 떠다녀. 그리고 비싼 총들이 색깔만 다른 것 같아."

둘 다 맞는 지적이었다.

## 손이 떠 있던 이유

총 모형은 도구(곡괭이) 틀에서 시작했다. 도구용 팔 상자를 총 옆에 그대로 붙여 놓으니,
손잡이(가로 0.09)보다 손(가로 0.17)이 커서 **총 옆에 흰 상자가 따로 뜬 것처럼** 보였다.
게다가 손목·팔뚝이 없어서 어디에 붙은 손인지도 알 수 없었다.

이제 어느 총이든 같은 규칙으로 붙인다:

```js
function gunGrip(g, gx, gy, gz, front){
  g.add(boxM(T.wool, 0.185,0.215,0.195, gx, gy, gz));               // 손잡이와 겹치는 주먹
  g.add(boxM(T.wool, 0.155,0.26,0.155, gx-0.02, gy-0.21, gz-0.10)); // 화면 아래로 이어지는 팔뚝
  if(front !== undefined) g.add(boxM(T.wool, 0.165,0.165,0.185, 0,-0.03, front));  // 앞손
}
```

긴 총에는 **앞손**이 총열을 받친다. 손 하나로 긴 총을 들면 떠 있어 보인다.

> 검사에 **"떠 있는 조각이 하나도 없다"** 를 넣었다.
> 일곱 자루의 모든 조각에 대해 '다른 조각과 상자가 닿아 있는지' 를 실제로 계산한다.
> 이 검사가 있었으면 처음부터 잡혔을 것이다.

## 총구가 나를 겨누고 있었다

모형은 +z 를 '앞'으로 놓고 만들었는데 카메라 앞은 -z 다. 반 바퀴를 안 돌려서
**여섯 자루가 전부 총구를 나에게 향한 채** 들려 있었다. 그래서 총열이 화면 오른쪽
뒤로 빠져 안 보이고, 개머리판만 보였다.

거기에 총열이 조준선과 거의 나란하면 화면에서 점으로 뭉개진다. 조금 비스듬히 들도록
`GUN_YAW` 을 줘서 총열이 화면을 가로지르게 했다.
방향·각도·크기를 `gunFinish()` 한 곳에서만 정하도록 모아 뒀다 — 일곱 자루를
따로 만지면 반드시 하나가 어긋난다.

## 여섯 자루가 각자 다르게 생겼다

색만 바꾼 회색 막대/금색 막대였다. 값이 열 배 차이 나는데 산 것 같지가 않았다.

| 무기 | 실루엣 |
|---|---|
| 🎯 나무 새총 | Y자 나무 가지 · 고무줄 두 줄 · 가죽 주머니 |
| 🔫 돌 화승총 | 긴 나무 개머리 · 놋쇠 테 · **타는 불씨**(빛남) |
| 🔩 쇠 소총 | 강철 몸통 · **옆으로 튀어나온 노리쇠** · 가늠자/가늠쇠 |
| 💨 연발총 | 짧고 두꺼운 몸통 · **아래로 긴 탄창** · 접이식 개머리 |
| 🏆 금빛 저격총 | 금 몸통 · **큼직한 조준경(빛나는 렌즈)** · 소음기 · 양각대 |
| 💎 수정 광선총 | **빛나는 수정 코어** · 금 링 두 개 · 떠 있는 조각 · 발광 방출구 |

## 성능 — 상자 하나가 곧 그리기 한 번이다

손에 든 모형은 인스턴스가 아니라 상자 하나하나가 따로 그려진다. 그래서 재 봤다.

| 든 것 | 드로우콜 | 곡괭이 대비 |
|---|---|---|
| 곡괭이 | 182 | — |
| 맨손 돌 | 175 | −7 |
| 새총 | 183 | +1 |
| 화승총 | 185 | +3 |
| 소총 | 186 | +4 |
| 연발총 | 185 | +3 |
| **저격총** | 191 | **+9** |
| 광선총 | 186 | +4 |

제일 비싼 저격총이 제일 비싸다(+9, 교실 크롬북에서 약 0.5ms). 한 번에 한 자루만
보이므로 이게 전부다. 조준경·양각대를 붙인 값으로 받아들일 만하다.

# 11차 손질 — 배포 배지 자리 피하기 + 최적화 검사

> "애들 크롬북 왼쪽 아래 powerd by netlify 칸이 있어서 거기에 총알 발사하는 버튼이
> 겹쳐. 위치를 옮겨줘야돼. 그리고 최적화 검사해줘."

## 1. 왼쪽 아래 구석 비우기

먼저 재 봤더니 배지에 걸치는 건 발사 버튼이 아니라 **조이스틱**이었다.
터치가 되는 크롬북은 `'ontouchstart' in window` 로 터치 모드가 켜지고,
그때 `#stick` 이 `left:16px; bottom:16px` — 배지 바로 그 자리에 앉는다.

- CSS 에 `--badgeH:52px` 를 두고 조이스틱·큰 버튼을 그 위로 올렸다.
- 아래 트레이(`#dock`)는 가운데 정렬이라 화면이 좁아질수록 왼쪽으로 자란다.
  1024폭에서 왼쪽 끝이 96px 까지 내려와 배지 밑으로 들어갔다.
  넓은 화면까지 손해 보지 않으려고, 실제 폭을 재 보고 **닿을 때만** 위로 올린다
  (`fitDock()`). 1366×768 교실 크롬북은 그대로다.
- 좁은 화면에서 `#hint` 를 숨기던 규칙 두 개를 없앴다. 예전엔 그냥 조작 안내였지만
  지금은 '지금 할 일' 한 줄이라 9살한테는 이게 제일 중요하다 — 숨기지 말고 줄인다.

짧은 화면에서 원래 있던 겹침도 이참에 다 잡았다 —
오른쪽 위를 세로줄(`#topRight`)로 묶고, 높이별로 지도·버튼·소식줄을 줄인다.
10가지 화면 크기 × 모든 짝을 검사로 못 박았다.

## 2. 최적화 검사 — 잰 것과 고친 것

교실 크롬북(Mali-G72 MP3)은 **드로우콜 하나가 약 60마이크로초**다.
삼각형보다 그리기 횟수가 훨씬 비싸다. 그 잣대로 봤다.

### 고친 것 ① 건물 색만 다시 칠하기 (제일 큰 CPU 이득)

밤에는 늑대가 벽을 계속 물어서 '건물이 바뀌었다'가 초당 12번 켜졌고,
그때마다 `rebuildStru()` 가 **건물 119채 · 블록 7700칸의 행렬을 통째로** 다시 만들었다.
개발 PC 로 4.0ms — 크롬북이면 한 프레임을 통째로 잡아먹는 턱이 초당 12번 생긴다.

그런데 물렸을 때 실제로 바뀌는 건 **색 하나**뿐이다(다칠수록 어둡고 붉게).
자리·크기는 짓거나 부수거나 강화할 때만 바뀐다. 그래서 둘로 갈랐다.

- `markShape()` — 짓기·부수기·강화 → 통째로 다시 (예전 그대로)
- `markHp(o)` — 물림·수리·아침회복 → **색만** (`tintStru`)

통째로 만들 때 블록이 어느 메시 몇 번째 칸에 들어갔는지 표(`_rk`/`_ri`)를 적어 두고,
색칠할 땐 그 칸만 `setColorAt` 한다.

| | 예전 | 지금 |
|---|---|---|
| 벽 14채가 물렸을 때 | 4.0 ms (전부 다시) | **0.12 ms** (그 채만) |
| 초당 12번이면 | 0.79 ms/프레임 + 4ms 턱 | 0.02 ms/프레임 · 턱 없음 |

검사로 **색만 고친 결과가 통째로 만든 결과와 981칸 전부 같음**을 못 박았다.

### 고친 것 ② 수정을 한 덩이로 (그리기 33 → 10)

수정은 마을 한가운데라 거의 언제나 화면에 있다. 그런데 보석 7층 + 도는 조각 7개 +
고리 알갱이 12알을 **따로따로** 그려서 그것만 33번이었다(크롬북 약 2.0ms).
모양도 재질도 같으니 인스턴스 메시 세 덩이로 묶었다 → **10번**.

프러스텀 컬링은 켜 둔 채다 — 자기 문 앞에서 바깥을 볼 땐 아예 안 그려야 하므로,
인스턴스 메시가 만든 boundingSphere 를 한 번 만들고 흔들리는 만큼 넉넉히 키웠다.

### 고친 것 ③ 손에 든 모형 굽기 (곡괭이 10 → 1, 저격총 19 → 4)

손에 든 것은 인스턴스가 아니라 상자 하나가 곧 그리기 한 번이다.
조각들은 서로 움직이지 않고 그룹 통째로만 흔들리므로, **같은 재질끼리 지오메트리를
미리 합쳐 구워** 뒀다(`bakeHeld`). three.js 의 BufferGeometryUtils 는 따로 받아 와야 해서
안 쓰고 직접 합친다 — 인터넷이 막힌 교실에서도 열려야 하는 파일 하나 원칙.

| 든 것 | 예전 | 지금 |
|---|---|---|
| 곡괭이 | 10번 | **1번** |
| 망치 | 7번 | **1번** |
| 저격총 | 19번 | **4번** |
| 광선총 | 19번 | **4번** |

굽기 전 조각 목록은 `userData.parts` 에 자리만 적어 남긴다 — 안 그러면
'손이 총에서 떨어져 떠 있나' 같은 검사를 잃는다(실제로 있었던 버그다).

### 고친 것 ④ 길찾기 안쪽 (4.4ms → 1.7ms)

길찾기는 칸 21609개 × 이웃 8 = 17만 번을 도는데 `for(const [dx,dz,w] of NB)` 로
매번 배열을 풀어 헤치고 있었다. 숫자만 꺼내 쓰는 납작한 배열로 바꿨다.
대각선 값은 `Float32Array` 에 넣으면 1.41 이 1.4099999666 으로 반올림돼
비슷한 두 길 중 고르는 게 달라질 수 있어서, 보통 배열로 뒀다.

**되돌린 것:** 한때 '벽이 부서져도 0.3초에 한 번만 다시 깐다'로 미뤄 봤다.
15일차 밤을 24판 돌려 보니 애들이 버티는 비율이 눈에 띄게 달라졌다(10/12 → 7/12).
끊김을 줄이자고 늑대가 움직이는 방식을 건드리면 안 된다 — 되돌렸다.
되돌린 뒤 다시 15판씩 돌려 옛 판 10/15, 새 판 9/15 로 같음을 확인했다.

# 12차 손질 — 경험치·스텟(C) · 더 사나워진 늑대 · 탑 제한 풀기

## 1. 늑대 — 체력과 걸음, 그리고 "바보가 되는" 문제

**재 본 것부터.** 선생님이 말한 "양이 도망치면 늑대가 양만 따라다니며 바보가 된다"를
하네스로 재 봤더니 그대로였다 — **옛 판에서는 늑대가 도망치는 양을 영영 못 잡는다.**

| 4칸 앞선 양이 최고 속도로 도망칠 때 | 옛 판 | 새 판 |
|---|---|---|
| 1일차 늑대 | 못 잡음 | **4.2초** |
| 8일차 늑대 | 못 잡음 | **4.2초** |
| 14일차 늑대 | 못 잡음 | **2.4초** |
| 8일차 날쌘늑대 | 못 잡음 | **2.4초** |

늑대의 걸음이 양(5.4)보다 느렸기 때문이다. 그래서 아이 하나가 뒷걸음질만 쳐도
늑대 열네 마리가 그 뒤만 졸졸 따라다녔고, 수정도 벽도 아무 일이 없었다.

고친 것:

- **기본 걸음 +20%** (늑대 2.6→3.15 · 날쌘 4.5→5.35 · 큰 1.9→2.30 · 보스도 같은 비율)
- **날이 갈수록 더 빨라짐** (+30% → **+42%**)
- **쫓을 땐 바닥값을 깐다 (`chaseMin 6.0`)** — 곱만 쓰면 1일차 늑대가 4.9밖에 안 돼서
  여전히 못 잡는다. 무슨 일이 있어도 양(5.4)보다 빠르다. 위쪽 뚜껑은 6.45 다
  (9살이 아예 손을 못 쓰면 게임이 아니라 벌이 된다).
- **쫓기 시간(`chaseBudget 5.5초`)** — 이게 핵심이다. 헛쫓은 시간이 다 되면
  **7초 동안 양을 잊고 수정·건물로 돌아간다.** 물면 시간이 다시 찬다.
  도망은 여전히 쓸모 있는 수(잠깐 벌어 준다)지만, 밤을 무력화하는 수는 아니게 된다.

효과 (입구 앞에서 반지름 5칸으로 계속 도는 아이 하나 · 늑대 14마리 · 60초):

| | 나를 쫓는 늑대 | 그동안 수정이 받은 피해 |
|---|---|---|
| 옛 판 | 평균 **14.0마리** (전부) | 0 |
| 새 판 1일차 | 평균 4.6마리 | 945 |
| 새 판 14일차 | 평균 8.6마리 | 1600 |

**체력은 1일차부터 마지막 밤까지 골고루 1.85배 → 3.10배로 올렸다.**
그리고 12일차와 15일차가 둘 다 마리수 상한(62)에 걸려 **똑같은 밤**이었던 것을 고쳤다 —
상한을 74 로 올려 12일차 52마리 · 15일차 61마리로 갈라진다
(보스 부하 최대 14를 더해도 늑대 렌더 상한 92를 안 넘는다).

## 2. 경험치 · 레벨 10 · 스텟 (C)

| 수리 | 6 |
| 늑대에게 준 피해 1 | 0.09 |
| 내가 잡으면 | +12 |

**만렙 10.** 레벨마다 스텟 1점(시작 1점 + 레벨마다 1점 = 10점).

| 스텟 | 최대 | 한 단계마다 |
|---|---|---|
| ⛏️ 캐는 손 | 5 | 캐는 속도 11% 빨라짐 |

**속도 스텟은 일부러 안 넣었다.** 넣으면 "늑대가 무조건 양보다 빠르다"와 부딪힌다.

## 4. 밸런스 — 얼마나 어려워졌나

하네스(bal5)는 다섯 문을 다 지어 놓고 밤을 통째로 돌린다.
아이들이 쏘고 · 밤에 수리하고 · 위험한 입구로 몰려가는 것까지 흉내 낸다.
탑 개수는 제한을 푼 뒤 교실에서 나올 법한 수(화살탑 9 · 얼음탑 5 · 배럭 3)로 잡았고,
사격에는 스텟으로 오른 공격력을 곱했다. 다섯 판씩 돌린 값이다.

**총 8명이 쏘고 8명이 수리 · 명중률 75%**

| 방어선 | 12일차 (옛 → 새) | 15일차 (옛 → 새) |
|---|---|---|
| 전부 Lv6 | 5/5 → 5/5 | — → **3/5** |
| 전부 Lv5 | 5/5 → **4/5** | 1/5 → **0/5** |
| 전부 Lv4 | — → **1/5** | — |

**참여한 사람 수로 보면 (전부 Lv6 · 15일차)**

| | 15일차 |
|---|---|
| 반쯤만 참여 (총4·수리4) | **0/5 패배** |
| 보통 (총8·수리8) | **3/5** |
| 반 전체 (총14·수리10) | 5/5 |

즉 예전엔 "보통만 해도 마지막 밤을 넘겼다" 였는데,
이제 **보통으로는 다섯 판 중 두 판을 진다.** 마지막 밤은 반 전체가 움직여야 한다.
더 어렵게 하려면 선생님 패널의 **늑대 세기**를 올리면 된다(이 값과 곱해진다).

# 12차 손질 (이어서) — 늑대가 목표를 갈아탄다

> "늑대가 양을 따라가면 끝까지 따라가서 죽이고 다른 곳으로 눈을 돌리더라고.
> 양을 따라오다가도 건물, 수정이 주변에 있으면 그것으로 목표 타겟을 바꾸고
> 부수다가 다시 양이 가까이오면 양 따라가고 이랬으면 좋겠어."

앞에서 넣은 '쫓기 시간(chaseBudget)'이 한 걸음 부족했다. 시간이 다 되기 전까지는
**목표가 그 양 하나로 못 박혀 있어서**, 옆에 벽이 있어도 수정이 코앞이어도 양만 봤다.
그래서 목표를 '고정'이 아니라 **'지금 제일 가까운 것'** 으로 바꿨다.

## 어떻게 정하나

늑대는 매 순간 이렇게 고른다.

1. **양이 코앞(1.9칸)이면** 무조건 양 — 사실상 이미 물고 있다.
2. 그보다 멀면 **거리로 겨룬다** — 지금 노리던 탑·배럭 / 곁에 있는 아무 건물(벽 포함) /
   7칸 안에 있는 수정.
3. **양이 15%는 더 가까워야** 목표를 도로 가져온다(`sheepBias 0.85`).
   딱 붙여 두면 반 칸 차이로 목표가 왔다 갔다 하며 제자리에서 떤다.

곁눈질할 건물은 6칸 안에서 찾고, 매 프레임이 아니라 0.6초에 한 번만 찾는다 —
양을 쫓는 늑대만 부르므로 값이 거의 안 든다(늑대 88마리에서 시뮬 0.72 → 0.80ms).

## 재 본 값

아이 하나가 **입구 앞에서** 반지름 5칸으로 60초 동안 계속 도는 상황.

| | 직전 판 | 지금 |
|---|---|---|
| 4일차 · 나를 쫓는 늑대 | 3.1마리 | **0.2마리** |
| 4일차 · 건물에 준 피해 | 1,131 | **1,702** |
| 12일차 · 나를 쫓는 늑대 | 7.4마리 | **1.9마리** |
| 12일차 · 건물에 준 피해 | 11,799 (8채 부숨) | **15,202 (12채 부숨)** |

즉 **끌고 다녀도 늑대가 안 따라온다.** 대신 옆에 있는 벽·탑을 부순다.

## 5. 대장간 — 무기 강화 +6 (요청 4·9)

수정 건너편(상인 반대쪽)에 대장간을 세웠다. `G` 로 연다. 낮에만.
상인과 반대편에 둔 이유: 같은 쪽에 두면 낮에 스물한 명이 한 자리에 뭉쳐 서로 화면을 가린다.

| 단계 | +1 | +2 | +3 | +4 | +5 | +6 |
|---|---|---|---|---|---|---|
| 성공 확률 | 80% | 65% | 50% | 35% | 20% | 20% |
| 공격 배수 | 1.12 | 1.26 | 1.42 | 1.62 | 1.86 | **2.15** |

**+3 까지는 실패해도 안 내려간다**(재료만 없어진다). +4 부터 내려갈 수 있다.

★ **"내려간다"를 반드시 내려가게 두면 안 된다 — 재서 알았다.**
확률 1.0 이면 +6 까지 **기대 시도가 172회**다. 40분 수업에서는 아무도 +6 을 못 본다.

| 하락 확률 | +4까지 | +5까지 | +6까지 |
|---|---|---|---|
| 1.0 (반드시) | 11회 | 43회 | **173회** |
| 0.5 | 10회 | 24회 | 58회 |
| **0.35** | **9회** | **20회** | **40회** |
| 0 (안 내려감) | 8회 | 13회 | 18회 |

`ENH_DROP = 0.35` 로 뒀다. **+4 는 여럿이 달고, +5 는 자랑거리, +6 은 반에 한둘 나오는 전설**이 된다.
화면에도 "실패하면 35% 확률로 한 단계 내려가요" 라고 정확히 적어 준다 — 누르기 전에 알아야 한다.

### 강화 보상 균형 (요청 9)

**값을 그 무기의 원래 값에 비례하게** 만든 것이 균형 장치다.
그래서 싼 총은 싸게 올리고 비싼 총은 아주 비싸게 올린다.

14일차 기준 · 몬테카를로 4000판으로 잰 값:

| 무기 | +0 초당 | +6 초당 | +6 까지 기대 재료 |
|---|---|---|---|
| 🎯 나무 새총 | 113 | 243 | 🪵1505 ✨92 |
| 🔩 쇠 소총 | 348 | **749** | 🪵839 🪨2945 ✨429 |
| 🏆 금빛 저격총 | 498 | 1070 | 🪨3462 ✨1557 |
| 💎 수정 광선총 | 664 | 1427 | 🪵3391 🪨3391 ✨2634 |

**쇠 소총을 +6 하면 초당 749** 로 생짜 저격총(498)을 넘지만,
드는 금이 저격총 값(✨34)의 **열두 배**다. 게다가 저격총은 사거리 34칸·한 방이 세다.
즉 "싼 총을 올리면 초당 화력, 비싼 총은 한 방과 사거리" 로 갈린다 —
**어느 한쪽이 늘 정답이 되지 않는다.**

★ 강화는 **무기마다 따로 쌓인다.** 안 그러면 싼 총으로 올려 두고 비싼 총을 사는 게 늘 정답이 된다.
★ 맨손 돌은 강화할 수 없다(값이 없는 무기다).
★ 결과는 각자 자기 화면에서 굴린다 — 남에게 영향을 안 주는 내 물건이라 통신을 한 겹 더 쓸 이유가 없다.

  화덕 불은 아예 스스로 빛나는 재질(`EMITC`)로 바꿨다 — 밤에도 대장간이 어디 있는지 보인다.

  곡선을 눕히자 '강화하면 경험치를 준다' 가 **−20** 으로 나왔다. 합계로 재야 한다.
  (t15 는 13차에 같은 이유로 이미 고쳤는데 t14 는 안 고쳐져 있었다.)
- **스크린샷을 찍다가 세 번 헛다리를 짚었다.** 카메라를 대장간에서 뒤로 물리면

  **양의 전방은 `(-sin yaw, -cos yaw)` 로 늑대·병사와 정반대다**(4차에 같은 것으로 양이 뒤를 봤다).

## 1. "강화했는데 안 빛나요" — 내 총에는 빛을 안 붙였다

14차에서 빛을 **남의 총(P_gunF)에만** 붙였다. 그런데 아이가 제일 오래 보는 총은
**자기가 든 총**이다. 대장간에서 +6 을 만들고 나와도 자기 화면에서는 아무 일도 안 일어났다.
"남들은 보이는데 나는 안 보인다" — 자랑할 데가 없으니 강화할 맛도 안 난다.

1인칭 총에도 빛 조각 둘을 붙였다(총열을 감싸는 후광 + 총구 불티).
단계별 모습은 **남의 총과 같은 표(ENH_FX)** 를 쓴다 — 두 곳이 어긋나면
"친구 총은 빨간데 내 총은 안 빨개요" 가 된다.

★ **크기를 세 번 헛짚었다. 셋 다 화면에 찍어서 잡았다.**

| 시도 | 결과 |
|---|---|
| `glow` 값을 그대로 씀 (1.30배) | **화면 오른쪽 아래가 주황 덩어리**가 됐다 |
| 그래서 확 줄임 (0.78배) | 후광이 **총 속에 파묻혀** 아예 안 보였다 |
| 총 몸통 크기를 실제로 **재서** 1.02~1.48배 | 어느 단계에서도 '총을 감싼 테두리' 로 보인다 |

카메라 코앞에 두는 것은 반드시 따로 재야 한다 —
**10차 총구 화염, 12차 레벨업 축포에 이어 세 번째**다.
그래서 표에 `fp`(1인칭 전용 크기) 칸을 따로 냈다. `glow`(남의 총)와 값이 다르다.

★ **맥동 폭이 단계 간격보다 크면 안 된다.** 처음엔 ±14% 로 숨쉬게 했는데
단계 사이 간격이 8% 뿐이라, 어느 순간에는 **+1 이 +3 보다 커 보였다**(검사가 잡았다).
±7% 로 줄이고 간격을 넓혔다. 단계 구분은 크기가 아니라 **색**이 맡는다.

★ **+4 부터는 손이 떤다.** 화면을 흔들지 않고 '손에 든 것' 만 떤다 —
화면을 흔들면 조준이 어려워져서, 9살이 +6 을 만들고 나서 오히려 못 맞히게 된다.
강화가 상이어야지 벌이 되면 안 된다.

★ 그리기는 **최대 2번** 늘어난다(한 번에 한 자루만 보이므로). 재질은 하나를 돌려 쓴다.

## 2. 강화 값 20%↓ · 공격력 증가분 10%↓ (요청)

## 3. 상인·대장장이 — "이상한 인형" 이었던 이유

> 세 가지였다. 4차에 병정을 고칠 때("가로가 세로보다 길어서 판자처럼 보였다")와 같은 진단이다.

1. **머리가 몸통만큼 넓었다** (0.52 대 0.62). 사람은 어깨가 머리보다 훨씬 넓다.
2. **목도 다리도 없었다.** 몸통 한 덩이가 바닥까지 내려왔다.
3. **상인은 팔이 아예 없었다.**

고친 것 — 둘 다 같은 처방:

- **다리를 둘로 갈랐다.** 이거 하나로 '서 있는 사람' 이 된다. 신발·장화를 붙였다.
- **목을 넣었다.** 머리가 '얹힌' 게 아니라 '달린' 것이 된다.
- **몸통을 허리/가슴 두 단으로** 나눠 어깨를 넓혔다 (상인 0.62 · 대장장이 0.86).
- **팔을 `rz` 로 기울여** 달았다. 곧게 내리면 다시 인형이 된다
  (4차에 연 '옆으로 기울이기' 를 여기서 처음 사람에 썼다).
- **실루엣을 갈랐다** — 상인은 챙 넓은 모자, 대장장이는 넓은 어깨와 **든 망치**.
  둘 다 '수정 옆에 선 사람' 이라 멀리서 헷갈리면 애들이 엉뚱한 데로 간다.

★ **대장장이가 갈색 덩어리 하나로 보였다.** 웃옷·앞치마·바지를 다 짙은 갈색으로 뒀기 때문이다.
4차에 건물에서 배운 것과 같다 — **재질 대비가 없으면 조각을 아무리 붙여도 안 읽힌다.**
웃옷을 밝은 적갈색으로 올리고 앞치마·바지는 짙게 남겨 세 층이 갈리게 했다.

★ **'눈썹 위 그늘' 로 어두운 띠를 얹었다가 이마를 통째로 덮어 얼굴이 사라졌다.**
빼고 눈썹만 가늘게 남겼다.

★ **모루와 화덕 딱 가운데 세웠더니 양옆에 끼어 답답했다.** 0.35칸 앞으로 내보내니
셋이 '작업하는 자리' 처럼 배치됐다.

## 4. 화면 확인하다 알게 된 것 — HUD 를 끄고 봐야 한다

모형을 세 번 찍었는데 세 번 다 **가운데 안내판("1일차")이 얼굴을 가렸다.**
검사 스크립트에 HUD 를 잠깐 숨기는 스위치를 넣었다(`shot14b.mjs`).
모형을 평가할 때는 이걸 쓴다.

카메라도 두 번 헛짚었다 — 대장간에서 **뒤로 물러나면 원점(수정 받침대) 속으로 들어간다.**
바깥쪽에서 안쪽을 봐야 한다.

## 5. 성능
